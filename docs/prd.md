# 可落地京东式商城系统（PC端专属·纯本地全容器化版）
## 业务架构与技术选型（Dubbo 3.x 纯开源栈·全K8s部署·开发环境优化）

## 一、核心定位与目标
- **用户规模**：支撑100-1000万注册用户，日活10-100万
- **并发能力**：峰值QPS 5000-20000，订单峰值1000-5000单/秒
- **架构目标**：服务化拆分完成，全容器化部署，具备完善的服务治理能力，支撑业务快速迭代
- **部署要求**：**100%本地部署+全容器化**，不依赖任何公有云服务，开发环境使用Docker Compose，生产环境使用K8s
- **运维理念**：开发阶段简单高效，生产阶段稳定可靠，环境一致性
- **终端范围**：仅PC端Web应用（含用户前台、商家后台、运营后台）

## 二、业务架构（DDD领域驱动设计）
### 2.1 核心业务域与微服务拆分（第三阶段标准）
采用**限界上下文**原则进行服务拆分，每个微服务对应一个独立的业务能力单元，拥有独立的数据库和缓存资源，开发阶段本地启动，生产阶段以K8s Pod形式运行。

| 业务域 | 拆分微服务 | 核心职责 | 部署方式 |
|--------|------------|----------|----------|
| **用户域** | 用户服务、认证授权服务、会员服务、地址服务 | 用户注册登录、身份认证、会员等级体系、收货地址管理 | 开发：本地IDE；生产：K8s Deployment |
| **商品域** | 商品基础服务、类目服务、库存服务、评价服务 | 商品全生命周期管理、分类体系、库存控制、商品评价管理 | 开发：本地IDE；生产：K8s Deployment |
| **交易域** | 购物车服务、订单服务、结算服务、退款服务 | 购物车管理、订单创建与状态流转、结算计算、售后退款流程 | 开发：本地IDE；生产：K8s Deployment |
| **支付域** | 支付服务、账户服务、对账服务 | 第三方支付渠道对接、资金账户管理、财务对账与清算 | 开发：本地IDE；生产：K8s Deployment |
| **营销域** | 优惠券服务、活动服务、积分服务、秒杀服务 | 各类营销活动管理、优惠券发放核销、积分体系、限时秒杀 | 开发：本地IDE；生产：K8s Deployment |
| **搜索域** | 搜索服务、索引同步服务 | 商品全文检索、过滤排序、索引实时同步与维护 | 开发：本地IDE；生产：K8s Deployment |
| **商家域** | 商家服务、店铺服务、商家结算服务 | 商家入驻审核、店铺装修与管理、商家对账与结算 | 开发：本地IDE；生产：K8s Deployment |
| **平台域** | 运营服务、风控服务、数据服务 | 平台运营配置、系统风控规则、业务数据分析与报表 | 开发：本地IDE；生产：K8s Deployment |
| **基础支撑域** | 消息服务、文件服务、通知服务 | 消息队列管理、文件存储与分发、短信邮件通知推送 | 开发：本地IDE；生产：K8s Deployment |

### 2.2 第三阶段核心业务流程
1. **商品上架流程**：商家创建商品 → 平台审核 → 商品服务持久化 → 库存服务初始化 → 发送事务消息 → 索引同步服务更新搜索引擎
2. **用户下单流程**：浏览商品 → 加入购物车 → 提交订单 → 库存服务扣减库存 → 订单服务创建订单 → 支付服务发起支付 → 支付回调 → 订单状态更新 → 通知商家发货
3. **售后退款流程**：用户申请退款 → 商家审核 → 退货物流确认 → 商家确认收货 → 退款服务发起退款 → 支付回调 → 订单状态更新 → 库存服务回补库存

- **一键启动**：一条命令启动所有中间件（13 个容器服务），5分钟内完成开发环境搭建
- **资源占用少**：单节点部署，适合开发机配置

## 六、GitLab CI/CD 全K8s部署方案
### 6.1 核心架构原理
采用**"全本地+K8s原生"**的CI/CD架构，实现从代码提交到服务部署的全自动化：
- GitLab和GitLab Runner全部运行在本地K8s集群上
- GitLab Runner使用**K8s执行器**，每次构建自动创建临时Pod，构建完成后自动销毁
- 构建产物（Docker镜像）推送到本地Harbor镜像仓库
- 通过K8s API直接更新Deployment，实现滚动发布
- 整个过程完全在本地K8s集群内完成，无任何外部依赖

### 6.2 标准CI/CD流水线
每个微服务使用统一的`.gitlab-ci.yml`模板，包含4个阶段：
1. **代码检查**：执行CheckStyle代码检查，确保代码质量
2. **构建测试**：编译代码，执行单元测试，生成构建产物
3. **镜像打包**：构建Docker镜像，推送到本地Harbor仓库
4. **部署**：更新K8s Deployment，实现滚动发布

## 七、第三阶段核心技术落地原则
### 7.1 服务拆分原则
- 优先拆分**用户、商品、订单、支付**四大核心服务
- 每个服务独立部署，拥有独立的数据库和缓存资源
- 服务间通过Dubbo RPC调用，避免跨服务直接访问数据库
- 非核心服务（如评价、通知）可在核心服务稳定后逐步拆分

### 7.2 数据架构原则
- 按业务域进行**垂直分库**，每个业务域对应一个独立数据库
- 对大表（订单、商品）进行**水平分表**，采用哈希分片策略
- 实施**读写分离**，一主多从架构，主库负责写，从库负责读
- 冷热数据分离，历史数据归档到单独的历史库

### 7.3 高可用原则
- 所有中间件和服务均采用**集群部署**，避免单点故障
- 核心服务（订单、支付）独立部署，与非核心服务隔离
- 配置完善的**限流、熔断、降级**规则，防止系统雪崩
- 建立完善的监控告警体系，实现故障快速发现和定位

### 7.4 性能优化原则
- 构建**多级缓存体系**（本地缓存Caffeine + Redis分布式缓存）
- 所有非实时操作全部**异步化**处理，通过消息队列解耦
- 对热点数据进行预加载和缓存预热
- 优化数据库索引和SQL语句，避免慢查询

### 7.5 部署原则
- **开发环境**：使用Docker Compose部署中间件，业务服务本地IDE启动
- **测试环境**：使用Docker Compose或轻量K8s集群部署所有服务
- **生产环境**：使用完整K8s集群部署，StatefulSet部署有状态服务，Deployment部署无状态服务
- 所有配置使用**环境变量**或配置中心管理，不硬编码在代码中

## 九、落地实施建议
1. **先搭开发环境**：优先使用Docker Compose搭建开发环境，让团队快速进入开发状态
2. **统一开发规范**：制定统一的代码规范、接口规范、日志规范和配置规范
3. **分阶段开发**：先开发核心服务（用户、商品、订单、支付），再开发非核心服务
4. **同步建设测试环境**：在开发进行到一定阶段后，搭建测试环境，进行集成测试
5. **逐步迁移到生产**：当核心功能开发完成并测试通过后，逐步迁移到生产K8s环境
6. **自动化运维**：利用GitLab CI/CD实现自动化构建和部署，减少人工操作
